# Phase 80 — UI Design Contract

> Visual and interaction contract for five new controls added to the EXISTING BrewPad **Waitlist**
> tab (Phase 78): customer link, recipe attach, contact/send, queue pin, manual add. Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.

**This is a static-HTML / vanilla-ES5 / hand-written-CSS project. No component library, no shadcn,
no Tailwind.** Every class and pattern below is cited to a `css/brewpad.css` or `js/brewpad.js` line
read directly during this research session (2026-09-04). This contract **extends, does not replace**,
`.planning/phases/78-.../78-UI-SPEC.md` — read that document first; every design decision it made
(Design System, Spacing Scale, base Typography rows, base Color roles, the table-not-cards layout
decision, the tap-to-cycle status badge, the loading/error/empty-state conventions) still applies
unchanged to this phase. This document only specifies what is **new or modified**.

**shadcn gate:** not applicable — static HTML/vanilla JS, no `components.json`. `Tool: none`.

**Governing rule for all new markup:** reuse over rebuild. Every net-new visual element below is
either (a) a verbatim reuse of an existing class/pattern with a new `id` namespace, or (b) explicitly
labelled "composed" — built only from existing tokens/classes/spacing, never a new spacing number, a
new font-size, or a new color.

## Phase-Specific Decisions

### 1. The table grows from 7 columns to up to 9 — add a horizontal-scroll wrapper, don't shrink cells

Phase 78 shipped: `#`, Email(+sync), [Category], Signed up, Status, Notes, Remove. This phase adds a
Customer-link affordance (absorbed into the existing Email/Customer cell, no new column), a Recipes
cell, and a Contact-action cell — net **+2 columns** (`#`, Customer, Recipes, [Category], Signed up,
Status, Contact, Notes, Remove = up to 9). At BrewPad's iPad-landscape usage width this would compress
every cell uncomfortably if forced to fit `width:100%` with no overflow. **Decision:** wrap the table
in a new `.bp-waitlist-table-wrap` div (`overflow-x:auto; -webkit-overflow-scrolling:touch`, copying
`#bp-recipes-ingredients-editor` verbatim) and give `.bp-active-batches-table` (as used here) a
`min-width` sufficient for 9 comfortable columns (recommend `960px`, following the ingredient editor's
`640px` for a narrower 5-column table, scaled proportionally) — **do not** shrink font-size, padding,
or truncate more aggressively than the existing Notes-column ellipsis to make columns "fit." Staff
already scroll the ingredient editor table on the same device; this is a proven, not novel,
interaction.

### 2. Customer-link and Recipe-attach both live INSIDE the row, expanding in place — no navigation, no modal-per-field

Both new sub-flows (search-or-create a contact; search-and-multi-select recipes) reuse the notes
inline-editor's "cell becomes an editor" transform rather than opening a separate sheet or navigating
away. Rationale: this phase's own `<code_context>`/`<canonical_refs>` in CONTEXT.md name these two
flows as **already-built, reused pieces** — the existing reassign panel and the existing recipe-attach
dropdown are themselves inline-in-place components, not sheet-based ones. Preserving that shape avoids
inventing a second interaction pattern for the same class of problem within a single row, and keeps
the table as the single source of navigational truth (Phase 78's Decision 1: "no detail to drill
into").

### 3. Contact button is disabled on `booked` and `removed` rows

Not explicitly locked by CONTEXT.md. **Decision:** the "Contact" button uses the same `actionable`
boolean already computed for the status badge (`status !== 'booked' && status !== 'removed'`,
`js/brewpad.js:8298`) — reusing an existing, already-correct predicate rather than inventing a second
one. Rationale: D-07's auto-advance write (`contacted`) would be a **backward** transition on an
already-`booked` row, which `waitlistTransitionAllowed` (Phase 78 CR-01) refuses server-side — offering
an action whose second leg (the status write) is guaranteed to fail, *after* an email has already been
sent, is a worse UX than not offering it. **Flagged for owner confirmation** — see Owner Review below;
if the owner wants "re-send a booking link to an already-booked customer" as a real use case, this
decision should be revisited together with a change to the backend transition rule, not silently
worked around in the UI.

### 4. D-23 disclosure renders as a sheet-state swap, not a toast

A toast is transient (a few seconds) and this message exists specifically so staff do not conclude an
add silently failed — the exact failure mode a toast risks reproducing if missed. **Decision:** on a
dedupe-match response, the Manual Add sheet's body area (`#bp-waitlist-add-sheet` → `.bp-create-sheet-
body`) swaps its `innerHTML` from the form to the disclosure message + a single `.btn-secondary` "OK",
staying open until the staff member deliberately dismisses it. This reuses the sheet shell (header,
close ×, backdrop-tap-to-dismiss) with zero new chrome — only the body content changes, exactly as
`renderWaitlist()` already swaps `#bp-panel-waitlist`'s inner content between loading/empty/populated
states.

### 5. Pin control is available on every row regardless of status

D-10 through D-14 do not restrict pinning to `waiting` rows, and the render-time merge-insert (80-
RESEARCH.md Pattern 2) sorts the *entire* table by position/signup-time regardless of status — so a
staff member could reasonably want to pin an already-`contacted` row higher in the visual list (e.g.,
to keep a VIP visible near the top while multiple people are mid-conversation with them). **Decision:**
render the pin affordance in the `#` cell for every row. For non-`waiting` rows (where
`computeWaitlistQueuePositions` never assigns a number), the cell shows `📌 —` when pinned (glyph
present, no rank number — there is no queue rank for a non-waiting row) or plain `—` when unpinned,
unchanged from Phase 78. **Flagged for owner confirmation** — see Owner Review below; the alternative
(restrict pinning to `waiting` rows only) is a one-line guard if the owner prefers a narrower scope.

### 6. Recipe chips never carry a remove-confirmation

D-16 makes recipes purely informational this phase (no batch/stock/pricing linkage) and D-15 allows
attaching/changing "at any time regardless of status" — removing a chip is fully reversible (the same
recipe can be re-attached in seconds) and carries no data-loss risk beyond re-typing a search term.
**Decision:** the chip's `×` writes immediately on tap, no `showConfirmSheet`, matching the same
low-friction bar Phase 78 set for notes edits (also freely re-editable) rather than the high-friction
bar set for the waitlist-Remove action (which is a genuine, D-05-flagged destructive exit from the
queue).

## Responsive / Accessibility Contract

*(Extends Phase 78's contract — only new elements listed; everything Phase 78 already established
for the tab, the table shell, the status badges, the confirm sheet, and focus states is unchanged.)*

- **Touch targets:** the "Contact" button, "+ Add to Waitlist" button, and both sheets' primary/

  pin icon and recipe-chip `×` follow the same **accepted exception** Phase 78 already documented for
  `.bp-reading-del` (icon-sized tap targets inside a dense table row, consistent with the existing
  readings-table edit/delete icons at the same scale) — not a new deviation.
- **Horizontal scroll (new this phase):** `.bp-waitlist-table-wrap` uses
  `-webkit-overflow-scrolling: touch` for native momentum scrolling on iPad Safari, matching the
  already-shipped `#bp-recipes-ingredients-editor` behavior on the same device.
- **Sheets (Contact review, Manual Add):** both reuse `.bp-create-sheet`'s existing, already-verified-
  on-iPad-Safari bottom-sheet chrome (backdrop tap-to-dismiss, `×` close, `env(safe-area-inset-bottom)`
  padding). No new gesture, no new modal machinery.
- **Focus states:** the sitewide `*:focus-visible { outline: 2px solid var(--stain); outline-offset:
  2px; }` (`css/brewpad.css:87`) applies automatically to every new interactive element with no extra
  CSS.
- **Semantic structure:** the Customer cell's inline search panel and the Recipe-attach panel both
  reuse existing labelled-input patterns (`placeholder` text doubling as the accessible name, matching
  every other BrewPad inline search input — no new labelling convention introduced). The pin icon
  button carries `aria-label="Pin this row's position"` / the clear control
  `aria-label="Clear pin"` / the Contact button (when disabled) needs no extra `aria-label` beyond the
  native `disabled` state, which screen readers already announce.
- **iPad Safari:** no new pinch/swipe interaction; `body { touch-action: pan-x pan-y }` (`:104`) is
  unaffected. The one genuinely new interaction shape (horizontal table scroll) is a **native browser
  behavior** on an already-`overflow-x:auto` element, not custom JS.
