not a new implementation.

<planner_decisions>
- **Both flows expand IN PLACE inside the row** (UI-SPEC Phase-Specific Decision 2) — the cell
  becomes an editor, exactly as `openWaitlistNotesEdit` does. No sheet, no modal-per-field, no
  navigation.
- **Do NOT reuse `_recipesState.list`.** It is populated only once `initRecipesTab()` has run, which
  requires staff to have opened the Recipes tab this session (`js/brewpad.js:2486-2492`). A staff
  member who opens BrewPad and goes straight to Waitlist would get an empty picker. Use the
  Batches-tab attach dropdown's own-lazy-fetch pattern instead (RESEARCH Pitfall 2 / Pattern 3).
- **D-03a is a real guard, not a nicety.** A manual add (plan 80-05) can put a hand-typed phone on a
  row. Linking a Zoho contact afterwards must not clobber it. Only write `customer_phone` when the
  row's current value is empty; always write `zoho_contact_id`; write `customer_name` unconditionally
  (it is a pure display cache with no manual-entry conflict once a contact is linked).
- **`customer_name` is never refreshed opportunistically** (D-03, discretion resolved in plan 80-01).
- **No remove-confirmation on recipe chips** (UI-SPEC Phase-Specific Decision 6) — removal is
  reversible in seconds, so the `×` writes immediately, matching the notes-edit friction bar.
- **Plan 80-03 owns `tests/frontend/brewpad-waitlist-render.test.js`; this plan only READS it.**
  Task 1 injects a `Link customer`/`Change` trigger into the Customer cell and Task 2 injects
  `+ Attach recipe` plus a chip `×` into the Recipes cell, and changes the chip label from the raw
  recipe id to the resolved recipe name — the same two cells that suite covers. 80-03 Task 2 pins
  those two cells' assertions to contains-style at authoring time, gated there, precisely so this
  plan's markup cannot invalidate them. So this plan reads the file to confirm compatibility before
  landing markup and runs it as a regression check, but modifies NO pre-existing test file — CLAUDE.md
  rule 10 applies here with no exception. If an exact-match assertion on a changed cell somehow
  survives into execution, STOP and surface it: do not edit the test, do not relax the assertion, and
  do not revert the trigger to keep it green.
</planner_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BrewPad -> `/api/contacts/search`, `POST /api/contacts`, `/api/recipes` | Existing endpoints reached with `credentials: 'include'` from a staff surface |
| Zoho contact data -> Waitlist sheet cells | Contact name and phone are copied into the shared Google Sheet |
| Zoho/recipe data -> BrewPad DOM | Search results and recipe names are rendered into innerHTML |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-80-22 | Tampering | XSS via a Zoho contact name/phone or a recipe name rendered into the row | mitigate | Every interpolated value goes through `escapeHTML` (`js/brewpad.js:57`), including `data-*` attribute values on result rows and chips; a test asserts a `<script>`-bearing contact name renders escaped |
| T-80-23 | Tampering | Sheets formula injection through `customer_name` / `customer_phone` / `recipe_ids` written from the browser | mitigate | Server-side `waitlistCellSafe()` on all four fields in plan 80-01's `updateWaitlistStatus` (D-19). The client performs no sanitisation of its own and must not be relied on |
| T-80-24 | Information disclosure | The contact search exposing the full Zoho customer list | accept | `GET /api/contacts/search` is a pre-existing endpoint already called from BrewPad's reassign flow and the kiosk; this plan adds a call site, not exposure. No change to its auth posture |
| T-80-25 | Tampering | A link write silently overwriting a manually-entered phone (D-03a) | mitigate | The write payload omits `customer_phone` entirely when the row's current value is non-empty; asserted by a dedicated test |
| T-80-26 | Elevation of privilege | Recipe attachment gaining downstream effect (stock, batch, pricing) | mitigate | D-16 scopes it to display-only; a grep gate asserts no `/api/recipes/` detail call and no `checkScaledStock` reference is introduced |
| T-80-SC | Tampering | npm/pip/cargo installs | mitigate | No packages installed — `80-RESEARCH.md`'s Package Legitimacy Audit confirms zero new dependencies phase-wide. slopcheck N/A |
