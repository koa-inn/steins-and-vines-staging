<planner_decisions>
**D-23 disclosure is derived client-side, and this is deliberate.** `addWaitlistEntry` returns the
byte-identical `{ok:true, id}` on both the new-row and dedupe-hit branches, and plan 80-01 keeps it
that way precisely because the public `POST /api/waitlist` path calls the same function. So BrewPad
derives the fact instead of being told it:

1. Validate the email client-side.
2. `adminApiGet('get_waitlist')` — a FRESH snapshot taken immediately before the write, so another
   staff member's add seconds earlier is still caught. Record the set of existing row ids.
3. `adminApiPost('add_waitlist_entry', { email: email, category: 'beer' })`.
4. If the returned `id` is IN the pre-write snapshot, it was a dedupe hit -> swap the sheet body to
   the D-23 disclosure, using the snapshot row's `signed_up_at` and status label (the pre-write
   values are the honest answer to "when did they sign up", since a `removed` row's reinstatement
   refreshes the timestamp). Write no optional fields and do not fire the MailerLite sync.
5. If the id is NEW: write the optional `customer_name` / `customer_phone` / `recipe_ids` via
   `adminApiPost('update_waitlist_status', ...)`, then fire
   `POST /api/waitlist/{id}/mailerlite-sync` (D-24), then close and toast.

There is structurally nothing new for the public path to leak, because no new field crosses the
Apps Script boundary.

**The booking link is resolved client-side from `GET /api/bookings/services`** — already public,
already 24h-caching `calcom.listEventType` results, already returning a real `bookingUrl`. Do not add
a Cal.com call and do not copy `sendBottlingInvite`'s hardcoded `CALCOM_BOTTLING_BOOKING_URL`
construction (RESEARCH Pitfall 3). Default to the ferment-kit service; the exact event type is
confirmed at plan 80-06's owner checkpoint.

**`signed_up_at` for a manual add is server-set to now** (D-25) — plan 80-01's `addWaitlistEntry`
already does this. Never send a backdated timestamp; staff who want to reflect earlier interest pin
the row instead.

**Contact button disabled on `booked`/`removed`** (UI-SPEC Phase-Specific Decision 3), reusing the
existing `actionable` predicate at `js/brewpad.js:8298` rather than inventing a second one. Flagged
for owner confirmation in plan 80-06.
</planner_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BrewPad -> `POST /api/waitlist/:id/contact` | Staff-tier; carries a staff-composed email body destined for a customer inbox |
| BrewPad -> admin proxy `add_waitlist_entry` | Staff-tier; injects a row into the same queue the public form writes to |
| BrewPad -> `GET /api/bookings/services` | Public endpoint read client-side for the booking URL |
| Waitlist row data -> the D-23 disclosure text | A customer's email, signup date and status rendered into the sheet body |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-80-27 | Information disclosure | The D-23 staff disclosure leaking onto the public `POST /api/waitlist` path and breaking Phase 78 D-06 | mitigate | The disclosure is derived entirely client-side by comparing the returned `id` against a pre-write `get_waitlist` snapshot; no new field crosses the Apps Script boundary and no file under `js/modules/` or `server.js` is touched. A grep gate asserts both |
| T-80-28 | Tampering | Retargeting a contact email to a different inbox from the sheet | mitigate | The `To` field is read-only and the sent value is read from the row object, never from the DOM input |
| T-80-29 | Tampering | Email-template injection via the staff-edited body | mitigate | Server-side `htmlEscape()` in `sendWaitlistContact` (plan 80-02 Task 1); the client sends plain text and performs no HTML assembly |
| T-80-30 | Tampering | The client marking a row `contacted` without a send | mitigate | No client code path writes `status`; the transition happens only inside the server's send-then-write sequence. A grep gate asserts no added `status: 'contacted'` line |
| T-80-31 | Elevation of privilege | A session-tier caller injecting arbitrary rows now that `add_waitlist_entry` is proxied | mitigate | Accepted consequence of D-21, bounded by the proxy's existing session-tier gate (plan 80-02 Task 3 adds the 401 test) and by `addWaitlistEntry`'s own email validation and dedupe.
