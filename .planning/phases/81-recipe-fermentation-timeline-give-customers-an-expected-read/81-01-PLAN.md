<objective>
Give the `Recipes` sheet a `schedule_id` column that persists a recipe's link to a
`FermSchedules` template, and close the pre-existing gap where editing a template never
invalidates the Apps Script `'gfs'` cache.

Purpose: D-03 makes the recipe→schedule link the single source of truth for the
customer-facing fermentation figure. Nothing downstream (middleware derivation, card
render, backfill) can work until the link can be stored. D-15's blast-radius warning ships
in this same phase and reads better against a cache that actually busts.

Output: `ensureRecipesScheduleIdColumn` plus its two call sites, `'schedule_id'` in
`updateRecipe`'s `stringFields`, a one-line cache-bust in each of the three FermSchedules
CRUD handlers, and a new Jest suite exercising the migration against a fake Sheets runtime.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| staff browser → Apps Script `doPost` (`create_recipe` / `update_recipe`) | Staff-supplied `schedule_id` string crosses into a spreadsheet cell |
| Apps Script → `Recipes` sheet cell | Untrusted string becomes persisted sheet content, potentially interpreted as a formula |
| `Recipes` sheet row → `get_recipes` staff response | The new field becomes readable by every staff-tier caller |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-81-01 | Tampering | `schedule_id` value written by `createRecipe`/`updateRecipe` | mitigate | Route the value through the existing `sanitizeInput()` (createRecipe uses it directly; updateRecipe gets it free by joining the `stringFields` array, which already applies `sanitizeInput` at `adminApi.gs:3769`) and through the existing formula-safety per-cell fallback in the batched-write path |
| T-81-02 | Tampering | `Recipes` sheet header row widened at runtime by `ensureRecipesScheduleIdColumn` | mitigate | Header write is append-only at `lastCol + 1` and guarded by `indexOf` so it is idempotent; the mandated ordering (ensure → `invalidateSheetCache` → `findRowById`) prevents a stale-width batched write from corrupting adjacent columns |
| T-81-03 | Information disclosure | `schedule_id` now present on every `get_recipes` row | mitigate | Source-side only. The public boundary is enforced in plan 81-02 by `PUBLIC_RECIPE_FIELDS` build-by-allowlist (T-74-04): `schedule_id` is never added to that array, so it cannot reach an anonymous caller. This plan deliberately adds no public exposure of its own |
| T-81-04 | Elevation of privilege | Apps Script action surface | accept | No new action is added to `doPost`'s server-token allowlist and no new action is added to `doGet`. `get_ferm_schedules` already exists on the read path and is already server-token reachable — the middleware will consume it in 81-02 with zero Apps Script surface change |
| T-81-05 | Denial of service | `'gfs'` cache eviction on every schedule CRUD call | accept | Schedule template edits are a rare staff action (a handful per year); losing a 300s cache entry costs one extra `getFermSchedules()` sheet read. Single-key `.remove` is used rather than `_invalidateBatchCache` specifically to avoid evicting hot batch-list keys |
| T-81-SC | Tampering | npm/pip/cargo installs | accept | N/A for this plan and this phase — no package is installed. RESEARCH.md § "Package Legitimacy Audit" records the phase as installing zero new dependencies, so the slopcheck gate has no subject |
</threat_model>
