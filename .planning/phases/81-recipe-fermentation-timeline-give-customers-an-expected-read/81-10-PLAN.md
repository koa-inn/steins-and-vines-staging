<the_defect>

`countRecipesUsingSchedule` (`js/admin.js:7646`) counts over `_recipesState.list`. That array is
filled only by `loadRecipeList()`, which is called only from `initRecipesTab()` — i.e. only once the
**Recipes tab has been opened**. The note is gated behind `if (usedByCount > 0)` at
`js/admin.js:7686-7693` inside `renderScheduleForm`, so an empty list renders nothing at all.

Confirmed empirically on staging in both directions (81-08 Task 3):

- Direct path (Admin → Batches → Schedule Templates → edit FS-0010): **no note**.
- Visit Recipes tab first (10 rows load), reopen the same FS-0010 modal: **"Used by 2 public
  recipes. Changing day offsets will change what customers are told."**

</the_defect>

<the_fix>

## Chosen approach: guarantee the load at the choke point, then render

`renderScheduleForm` has exactly two callers — `openCreateScheduleModal` (`js/admin.js:7622`, the
create form, where D-15 correctly shows nothing) and `openEditScheduleModal` (`js/admin.js:7626`,
the only path that renders the note). Put the guarantee in `openEditScheduleModal` and defer the
render until the count can be answered.

This mirrors the pattern 81-06 already used for `openScheduleActivateModal`'s pre-open loader
(a non-fatal async leg that always calls back before the modal opens), and it preserves 81-04's
guarded-idempotent property: **zero cost when the list is already loaded.**

## Where the load belongs — the tradeoff, decided

Three candidate sites were weighed:

| Site | Behaviour | Verdict |
|------|-----------|---------|
| Batches tab lazy-load (`triggerBatchLoad`) — the literal mirror of 81-04 | Starts a `/api/recipes` (+ `/api/ingredients`) fetch on every Batches visit and hopes it lands before Edit is clicked | **Rejected.** Pays for every Batches visit, most of which never touch templates, and is still a race. |
| Schedule Templates sub-tab handler (`initBatchSubTabs`, `js/admin.js:5631`) | Narrower pre-warm, still async, still hopes the fetch lands before the click | **Rejected.** Same race, just a shorter one. |
| `openEditScheduleModal` — the choke point | One fetch, issued exactly when the count is about to be rendered; none at all if the list is already there | **Chosen.** |

The deciding argument: a pre-warm makes the warning *usually* right. A warning that is
non-deterministically right is the same class of defect as one that is always wrong — and worse,
because it cannot be tested and will not reproduce on demand. The choke point makes it
unconditionally right.

**The cost, stated plainly:** the first template-edit modal of a session waits one round-trip
(~200-500ms) before opening, with no spinner. This is accepted — it is the identical tradeoff 81-06
already took for `openScheduleActivateModal`, on a modal opened far more often than this one.

## Contract for `ensureRecipeListForBlastRadius(cb)`

Colocate it with `countRecipesUsingSchedule` (`js/admin.js:~7646`). `cb` is invoked **exactly once
on every path**, success or failure.

1. If `_recipesState.list.length > 0` → call `cb()` **synchronously** and return. No fetch. This is
   the 81-04 idempotence property: costs nothing when the Recipes tab was already visited.
2. If `getRecipesMwUrl()` is falsy → `cb()`. Never let configuration block the modal.
3. Otherwise fetch `mwUrl + '/api/recipes?status=' + encodeURIComponent(status)` with
   `{ credentials: 'include', headers: getRecipesMwHeaders() }`, where `status` is resolved
   **exactly the way `loadRecipeList` resolves it** — `document.getElementById('recipes-status-filter')`'s
   value if the element exists and is non-empty, else `'all'`. Both paths must count the same
   population, or the count would differ by navigation path, which is the bug we are fixing.
4. On success: assign `_recipesState.list = data.recipes || []` **only if it is still empty** (do not
   stomp a Recipes-tab load that resolved in the meantime), then `cb()`.
5. On failure: `.catch(function () { cb(); })`. Silent, non-fatal, no toast. The modal always opens;
   the worst case degrades to today's behaviour (note absent) rather than a broken editor.

**Hoisting note (so you do not restructure the file):** `getRecipesMwUrl`, `getRecipesMwHeaders` and
`loadRecipeList` are declared later in the file (`js/admin.js:8616+`) but inside the same IIFE, so
function-declaration hoisting makes them callable from line ~7646. `_recipesState` is a `var`
initialised at module load, long before any click. No reordering is needed or wanted.

## Three things this function must NOT do

- **Must not call `loadRecipeList()` or `renderRecipeList()`.** 81-06 established this: those write
  `"Loading recipes..."` and then a full table into `#recipes-tbody`, leaking Recipes-tab table
  state into a Batches-tab interaction. Baseline `grep -c "loadRecipeList()" js/admin.js` is **5**
  and `grep -c "renderRecipeList()" js/admin.js` is **3**; both must be unchanged after this plan.
- **Must not set `_recipesDataLoaded` / `_recipesDataLoading`.** Those guard the Recipes tab's own
  init. Setting them here would make a later Recipes-tab visit skip `initRecipesControls()` and
  `loadIngredientCatalogForRecipes()`, breaking the tab.
- **Must not show a toast on failure.** A staff member editing a template did not ask for recipes.

## Do not touch

`countRecipesUsingSchedule`'s body or its comment block, the note markup at `js/admin.js:7686-7693`,
its copy, `availability-banner--low`, `openCreateScheduleModal`, `initBatchSubTabs`,
`triggerBatchLoad`, `initRecipesTab`, or anything in `buildCreateBatchFormInner`.

</the_fix>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin browser → middleware `GET /api/recipes` | Authenticated staff request; new call site, same endpoint and same session-cookie auth already used by `loadRecipeList` |
| middleware response → `#admin-modal-body` innerHTML | Server-controlled recipe data reaches a string built with `+=` and injected via `openModal` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-81-10-01 | Information disclosure | New `GET /api/recipes?status=…` call from the Batches tab | accept | Same endpoint, same `credentials:'include'` session auth and same status-filter value `loadRecipeList` already sends. No new data reaches the client and nothing new is rendered — only an integer count derived from `schedule_id`. The 81-08 leak greps (`schedule_id`/`steps_parsed`/`day_offset` absent from anonymous responses) are unaffected: this is an authenticated admin endpoint, untouched. |
| T-81-10-02 | Tampering (XSS) | `renderScheduleForm` note markup | accept | The note interpolates only `usedByCount`, a `.length` — a number, never attacker-controlled text. Markup unchanged by this plan. The pre-existing unescaped `existing.name` / `existing.description` interpolation at `js/admin.js:7677-7678` is out of scope here (staff-authored, pre-existing, not introduced or widened by this change) — record it in the SUMMARY as an observation, do not fix it in this plan. |
| T-81-10-03 | Denial of service | Modal open blocked by a hanging or failing fetch | mitigate | `cb()` is invoked on every path including `.catch`; the modal opens regardless. Failure degrades to today's behaviour (no note), never to a broken editor. Test 5 asserts this. |
| T-81-10-04 | Repudiation | Wrong count shown after a status-filter change | accept | Status resolution mirrors `loadRecipeList` exactly, so both navigation paths count the same population. The pre-existing lower-bound caveat is already documented in the comment at `js/admin.js:7635-7638` and the copy states consequence rather than a complete audit. |
| T-81-10-SC | Tampering | npm/pip/cargo installs | n/a | This plan installs nothing. No `package.json` change in either tree. If any task appears to need a dependency, stop — that is a scope error. |
