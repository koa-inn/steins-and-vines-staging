<objective>
Surface the BeerXML file's own fermentation claim in the import review modal, let staff attach a
schedule template there with both numbers visible, and carry that choice through to the recipe
form.

Purpose: D-12 applies this codebase's established "import informs, human confirms" control
(Phase 15 D-08/D-09) one level up, at the recipe field rather than the ingredient row. D-13
forbids auto-suggestion because a BeerXML timing field is frequently the exporting software's
untouched default, and pre-selecting from it is how a wrong timeline gets confirmed by reflex.
D-14 shows both numbers with no threshold and no judgement — a threshold would imply the file is
authoritative, which is exactly what the review step exists to deny.

Output: three new parsed timing fields, a meta-line segment, a filtered-not-hidden template
dropdown, a browser copy of the derivation function, a neutral comparison line, and the one-line
carry-through fix without which the whole dropdown is decorative.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| uploaded BeerXML file → browser DOM | A staff-supplied file is parsed client-side; its values reach the review modal's markup |
| Apps Script schedules → modal `<option>` markup | Staff-authored template names and categories are interpolated into a string-built modal body |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-81-22 | Tampering | `parsed.ferment_days_beerxml` interpolated into the meta-line HTML string | mitigate | The value is produced by `parseFloat(...) || 0` and summed, so it is always a JavaScript number by the time it reaches the string — a hostile file cannot smuggle markup through this field. It joins the existing `metaLine` builder that already interpolates `parsed.abv` and `parsed.batch_size_l` the same numeric way |
| T-81-23 | Tampering | `#beerxml-schedule-select` option markup | mitigate | Options come from `buildScheduleOptionsHtml` (plan 81-04), which applies `escapeHTML` to `schedule_id`, `name` and `category`. Reusing that single helper rather than writing a second loop keeps the escaping in one auditable place |
| T-81-24 | Tampering | `#beerxml-schedule-compare` content | mitigate | Set via `textContent`, never `innerHTML`. Both interpolated values are numbers (`ferment_days_beerxml` from `parseFloat`, `templateDays` from `maxNonPackagingOffset`'s `typeof === 'number'` filter) |
| T-81-25 | Spoofing | An untrusted BeerXML timing value influencing what a customer is told | mitigate | Structurally prevented. `ferment_days_beerxml` is display-only: it is never written to a recipe, never sent in a save payload, and D-13's no-pre-selection rule means it cannot even nudge the template choice. The public figure derives solely from the staff-chosen `FermSchedules` template (D-03). An acceptance criterion asserts no proximity-ranking function exists |
| T-81-26 | Repudiation | Silent discard of the staff member's template choice | mitigate | Task 3 closes the verified `confirmBeerXMLImport` carry-through gap, with an acceptance criterion asserting the read happens before `closeModal()`. Without it staff would believe they attached a schedule when they had not — a false record of their own decision |
| T-81-27 | Information disclosure | Schedule step data in the staff DOM | accept | `admin.html` is staff-only behind the Phase 46 Google-session tier, and `fermSchedulesData` is already fully present in the browser for the two existing batch dropdowns. This adds no new exposure class, and none of it crosses the public boundary (enforced in plan 81-02) |
| T-81-SC | Tampering | npm/pip/cargo installs | accept | No package is installed. RESEARCH.md § "Package Legitimacy Audit" records the phase as installing zero new dependencies |
</threat_model>
