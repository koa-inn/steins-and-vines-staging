DEPLOY REALITY — read this before ordering anything:
- Apps Script has ONE deployment serving staging AND production. There is no staging Apps Script.
- Staging and production share ONE Google Sheet. Any sheet write made while "testing on staging"
  hits live production data.
- Apps Script is outside `gated-deploy.yml`'s scope entirely (`docs/RUNBOOK.md`).
- The `schedule_id` migration is SELF-HEALING, not fail-closed. `ensureRecipesScheduleIdColumn`
  adds the column itself on first write. This is the `ensureRecipesPricingModeColumn` precedent,
  already live in production. It is NOT the Phase 80 Waitlist case: `ensureWaitlistSheet` is a
  fail-closed validator that returns `{ok:false}` when any of 13 headers is missing, which is why
  Phase 80 needed a manual "add the columns first" step. **There is no load-bearing manual
  pre-redeploy column addition here. Do not perform one.**
- Deploying the new code against the unmigrated sheet is safe by design: old rows read `''` and
  `sheetToObjects`/`findRowById` are header-name based, never positional, at all 13 `Recipes`
  call sites.

Read command for the inventory (owner runs it; the token is a secret and is deliberately not in
this working copy):
  curl -s "$APPS_SCRIPT_URL?action=get_ferm_schedules&server_token=$APPS_SCRIPT_SERVER_TOKEN"
Equivalent without a shell: in the Apps Script editor, run
  Logger.log(JSON.stringify(getFermSchedules()))
