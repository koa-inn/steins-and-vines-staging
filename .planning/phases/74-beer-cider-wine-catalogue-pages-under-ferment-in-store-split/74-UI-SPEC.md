# Phase 74 — UI Design Contract

**This is a static-HTML / vanilla-ES5 / hand-written-CSS project. All values below are cited to `css/styles.css` line numbers or `js/modules/07-catalog-kits.js` function names, read directly from the repository during this research session (2026-09-01).

## Phase-Specific Decisions (the 10 questions this contract must settle)

### 1. `/wine` is kits-only at launch — must look complete, not broken

Because D-04 fully suppresses a zero-item block, `/wine` will render exactly ONE `.catalog-section` ("Wine Kits") and nothing else where the recipe block would go — no bare "Wine Recipes" heading, no "coming soon," no empty grid. **This is sufficient on its own for the page to look intentional**, because it's identical in shape to how `products/ferment-in-store.html` already presents its single wine grid today (which nobody perceives as broken). No additional design element (no "more coming soon" banner, no placeholder card) is needed or wanted — adding one would contradict D-04's own rationale and would read as an apology for something that isn't missing.

### 2. `/beer` launches with a 1-kit block + 1-recipe block — the fragile single-card grid

**Root cause identified in this session:** `.product-grid` uses `grid-template-columns: repeat(auto-fit, minmax(280px, 1fr))` (styles.css:1526-1531). With exactly one grid item, `auto-fit` collapses to a single track and that track's `1fr` stretches to consume the full container width (up to `--max-width: 1100px`, 90% of viewport). A `.label-beer` bottle-card or a `.product-card` recipe card stretched to 900+px wide — while its internal typography stays fixed-size — looks like a huge mostly-empty rectangle with content marooned in the middle. This is the single most visually fragile state in the phase, and per the phase's own live data it IS the launch state (1 beer kit, 1 active recipe), not a hypothetical edge case.

**Locked fix — new modifier class `.product-grid--compact`:**
```css
/* Applied when a rendered grid group has ≤ 3 cards — prevents the
   auto-fit/1fr stretch from blowing a 1-2-card grid up to full width. */
.product-grid--compact {
  grid-template-columns: repeat(auto-fit, minmax(280px, 320px));
  justify-content: start;
}
@media (max-width: 480px) {
  .product-grid--compact { grid-template-columns: 1fr; justify-content: stretch; }
}
```
- `320px` matches the existing comfortable width of a `.label-wine`/`.label-beer` card at its natural size (its `minmax(280px, 1fr)` floor is 280px; 320px gives a touch of breathing room without competing with the 3+ card case).
- `justify-content: start` left-aligns cards under the section heading (also left/center-aligned via `.catalog-section-header { text-align: center }` — cards sitting left under a centered heading is acceptable; centering the grid itself, `justify-content: center`, is the alternative if the executor's visual QA prefers it — either is a reasonable call within this contract, but pick one and apply it consistently to both the kit and recipe grids on the same page).
- Apply this modifier to BOTH the kit grid and the recipe grid whenever their respective group has 3 or fewer cards. At today's live counts (1 beer kit, 1 active recipe), both grids get it. This threshold is deliberately conservative — 3 cards in the default `minmax(280px,1fr)` grid already look reasonably proportioned in a 1100px container (~345px/card); the defect is specifically at 1-2 cards.
- This is additive CSS next to the existing `.product-grid` rule — it does not touch `.product-grid` itself, so `products/ferment-in-store.html`'s ingredients grid (or any future higher-count grid) is unaffected.

### 3. D-03 tie-break — kits lead on a count tie (LOCKED)

At launch `/beer` has 1 kit and 1 active recipe — an exact tie, which D-03 itself doesn't resolve. **Locked decision: kits render first on a tie.** Rule: `kitCount >= recipeCount → [Kits block, Recipes block]`, else `[Recipes block, Kits block]`. Rationale (matches RESEARCH's own recommendation): kits are the more "shop-ready" of the two given the recipe list is presently a single item, and this doesn't fight D-11's requirement that the page's *narrative* sections (hero → What It Is → How It Works → What's Included) land before either catalogue block — by the time a visitor reaches the catalogue at all, they've already been told beer is booked-ahead. This is now a fixed rule, not an emergent property of whatever the sort happens to do — implement it as an explicit comparison, not an artifact of array order.

### 4. D-02 block differentiation — headings + card visual language

**Heading treatment:** each block gets its own `.catalog-section` → `.catalog-section-header` → `<h2 class="catalog-section-title">` (exact existing pattern, styles.css:1502-1516 / `renderSection()`). Headings: "Wine Kits" / "Beer Kits" / "Beer Recipes" (see Copywriting Contract). One-line sub-copy under each heading (also Copywriting Contract) makes the *purpose* difference explicit in words, not just implicit in layout.

**Card visual differentiation (does the real work — a visitor should tell kit vs. recipe apart without reading the heading):**
- **Kit cards** = the existing ornate "bottle label" idiom (`.label-wine` / `.label-beer`): double/gold border, centered ornament or SV-logo crest, serif/condensed display name, price-footer with a horizontal rule. This idiom visually says "physical product."
- **Recipe cards** = the plain `.product-card` idiom (white background, single 1px brown border + 3px burgundy top accent, left-to-right rectangular layout via `.product-card-header`). This idiom visually says "listing/service," not "product for sale" — appropriate since a recipe isn't a standalone purchasable SKU, it's what you brew when you join the waitlist.

These two idioms are already maximally distinct on production today (compare any wine kit card to `buildDefaultCard()`'s plain rendering) — reusing them as-is for kits-vs-recipes, rather than designing a third new visual language, is the lowest-risk way to satisfy "must not read as duplicates."

### 5. Recipe card anatomy (D-07)

Built entirely from existing, currently-dead CSS (`.product-card .service-description` / `.service-price`, confirmed unused by any JS today):

```
.product-card
├─ .product-card-header
│  ├─ h4 (recipe name — 1.4rem/700/Playfair Display/burgundy, product-card h4 :1596)
│  └─ .product-card-category  (style — 0.75rem/muted, :1624)
├─ .product-detail-row  (only if a secondary meta field is needed — omit for launch; style already lives in .product-card-category, don't duplicate it here)
├─ .service-description  (blurb — 0.9rem/1.5 line-height/--color-text, :1866. OMIT this element entirely if description is empty — see Copywriting Contract)
└─ .product-prices.service-price → .product-price-box
   └─ price value (formatCurrency(...), styled via existing .product-price-value)
```

**Field order, top to bottom: name → style → price → blurb.** This intentionally puts price ABOVE the blurb (not below), because D-07's whole point is that price is a first-class, safe-to-show field — burying it under a paragraph would undersell that it's meant to be scannable. (The kit cards already do the reverse — name → style → blurb-toggle → price-footer at the very bottom — because a kit card culminates in an add-to-cart action, so price sits right above the button. Beer's recipe card has no button, it terminates at the blurb + a waitlist link, so leading with price fits its shorter, non-transactional read.)

**Price computation (per RESEARCH's confirmed API contract):**
- `pricing_mode: 'dynamic'` → display `recipe.computed_price` (already fee-inclusive per `enrichListPrices()`, `zoho-middleware/routes/recipes.js:140-142`). If `computed_price` is `null` (ingredient data unavailable), omit the price line rather than showing `$0.00` or a dash — fall back to the label **"Price set when you book"** (matches existing beer.html "What's Included" copy: "We'll go through the options and give you a price when we book your session.").
- `pricing_mode: 'locked'` → display `locked_price + service_fee + materials_fee` (matches the site's existing "fee-inclusive" pricing decision recorded in `.planning/STATE.md`).
- Reuse the existing `pricing_from`/`+`-suffix convention already used on kit price footers (`plusSign` in `buildDefaultCard()`, `07-catalog-kits.js` ~line 1005) if the recipe's price can change with modifications/scale — label as **"From $X"** rather than a bare number, consistent with how kit prices already signal "starting at."

**Empty-description handling:** D-08 gates release specifically so this should not occur in production (the one active recipe's blurb will be written before ship). The card's layout must nonetheless degrade gracefully if it does: omit `.service-description` cleanly (no empty `<p>`, no visible gap larger than the section's normal `margin-bottom`) rather than rendering placeholder text.

### 6. D-12 beer card action — waitlist, not cart

**Both beer kit cards and beer recipe cards get the identical CTA treatment** — D-12 says "Beer cards lead to the waitlist," not "beer recipe cards"; RESEARCH's own architecture diagram and Pitfall 1 confirm `buildBeerCard()` (used for the one beer *kit*) needs its reserve/buy tail replaced too. There is no separate "buy this beer kit" path at all — beer is booked-ahead only, consistent with beer.html's own copy ("priced per recipe... give you a price when we book").

**Affordance:** a single `<a>` styled with the existing `.btn` class (burgundy bg, cream text, matches every other primary CTA on the site) reading **"Join the Waitlist"**, `href="#waitlist"` (in-page anchor — beer.html already has `id="waitlist"` on its waitlist `<section>`, so this is a same-page scroll, not a navigation). Replace the reserve/buy-control tail in `buildBeerCard()` (the two `reserveWrap`/`kitBuyWrapBeer` blocks, lines ~882-902) with this single link, occupying the same footer slot the price-footer/reserve controls currently sit in (so the card's overall silhouette doesn't change — only its bottom action changes from two buttons to one link). The new recipe card uses the same `<a class="btn" href="#waitlist">Join the Waitlist</a>` in its own footer slot, below the price line.

### 7. D-13 per-category filters — visual contract + risks

- **Wine `/wine` filter row set (unchanged):** Type, Brand, Producer, Style, Production Time, Body, Oak, Sweetness, Sale, Sort — the exact existing call list from `products/ferment-in-store.html` (13-init.js / 07-catalog-kits.js:194-201).
- **Beer `/beer` filter row set (new call list, not new panel):** Style (reusing the `subcategory` field/filter-row machinery), ABV (net new field). Conform to the same `.catalog-collapsible`/`.catalog-filter-row`/`.catalog-filter-btn` chip visual language Phase 77 already shipped (CSS-only, live 2026-08-28) — no parallel filter UI, no new panel chrome. The panel component itself needs zero visual changes; only the per-page call list differs.
- **Risk flagged (confirmed real by RESEARCH, still applies):** `buildFilterRow()`'s `subcategory` branch has a hardcoded wine-only sort order (`['red','white','rosé','rose','fruit','specialty']`, `07-catalog-kits.js:337-345`). Reusing "Style:" for beer subcategories (IPA/Lager/Stout/etc.) inherits this wine-specific sort unless conditioned on category — beer style values will fall through to the `else` branch (alphabetical `.sort()`, since none of them match the wine list, `aIdx`/`bIdx` both resolve to `styleOrder.length` and comparator returns 0 → stable insertion order in most engines, but not guaranteed). **Visual consequence to test:** beer style chips may render in an arbitrary/inconsistent order rather than a deliberate one. Recommend a simple category-conditioned branch (`if (field === 'subcategory' && category === 'beer') uniqueValues.sort();` — plain alphabetical is an acceptable, low-cost fix and is more defensible than silently inheriting wine's list) — this is implementation, but flagging it here because it's a visible ordering defect, not just a code smell.
- **ABV filter chip design (net new — this is the one piece of real filter engineering D-13 requires):** ABV values are free-text-ish strings like `"5.8"` or `"5.8%"` (confirmed live). Given the low item counts at launch (11 cider/1 beer, wine larger), an exact-value chip list (same pattern as every other `buildFilterRow()` field — no numeric bucketing/range slider) is sufficient and consistent with the site's existing filter idiom; do not build a range slider or bucketed-ABV UI for this phase, it would be new UI machinery the low item counts don't justify. Sort numerically ascending (mirror the existing `time` field's numeric-sort branch, `07-catalog-kits.js:331-336` — `parseFloat` before compare) rather than alphabetically, since "5.8%" vs "12%" needs numeric ordering to read sensibly.

### 8. D-10 hub rewrite — section structure + Ingredients tab disposition

**Hub page structure, top to bottom (page title unchanged: "Ferment-in-Store" — already category-neutral, no change needed):**

### 10. Empty / loading / error states — precise contract

- **Zero-item block (D-04):** never enters the DOM. Implement as an early-return in the block renderer (mirrors the existing pattern at `renderSection()`, `07-catalog-kits.js:1069` — `if (items.length === 0) return;`), not a CSS `display:none` on a rendered element. No heading, no wrapper, nothing.
- **Ordering requires BOTH counts before either block paints (consequence of D-03 + this section's tie-break rule):** do not render the kit block as soon as `/api/products` resolves and then pop the recipe block in later once `/api/recipes` resolves — that produces a visible reflow/reorder if the recipe block turns out to outrank or get suppressed. Show a single shared loading state (existing `.catalog-skeleton-grid`) until BOTH fetches settle, then commit the final block order + suppression + content in one paint.
- **Independent per-block error handling (new — the existing kit-only error handler is monolithic and replaces the whole `#product-catalog`):** if the recipe fetch fails while the kit fetch succeeds (or vice versa), the failing block shows its own small inline error (see Copywriting Contract's per-block error copy) scoped to its own section — it must NOT blank out a block that loaded successfully. This is new behavior this phase must build (the kit-only path today is all-or-nothing); flagging explicitly so it isn't treated as "just reuse `loadProducts()`'s existing catch block as-is."
- **Loading state visual:** reuse `.catalog-skeleton-grid`/`.skeleton-card` as-is (styles.css:1218), sized to roughly the expected 1-3 card count rather than a large placeholder grid, to avoid an oversized skeleton collapsing awkwardly once real (possibly single-card) content replaces it — this pairs with the `.product-grid--compact` fix in §2.
