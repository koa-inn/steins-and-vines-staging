<objective>
Make the shared kit catalogue category-aware so `/wine` and `/beer` can render their own kit block, switch beer kit cards from cart controls to the waitlist CTA (D-12), and give each category its own filter row set (D-13).

Purpose: `loadProducts()` today loads all of `KIT_CATEGORIES` (wine + beer + cider + seltzer) on every page that calls it, and `buildBeerCard()` — despite already existing — wires the same Reserve and Buy Kit cart controls that wine gets, which directly contradicts D-12. Beer is booked-ahead only.
Output: a category parameter on `loadProducts`, a waitlist action tail on beer cards, an ABV filter field that does not exist anywhere in the codebase today, and testable module-scope helpers for all three.

**Do NOT run `npm run build` in this plan.** `js/main.js` / `js/main.min.js` are regenerated once, in plan 74-06, after every `js/modules/*` edit in this phase has landed. Running it here would churn build artifacts that a parallel plan also stamps.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `GET /api/products` → browser | Public, unauthenticated, unscoped kit inventory. Category scoping here is a DISPLAY concern, not an access-control boundary — kit price/stock/tasting notes carry no sensitivity comparable to recipe cost data. |
| Zoho custom-field values → DOM | Untrusted upstream strings (`cf_type`, `cf_subcategory`, `abv`) rendered into filter chips and card text. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-74-08 | Tampering / XSS | new filter chips and the waitlist CTA node | mitigate | Every new node is built with `document.createElement` and `textContent` — no `innerHTML` and no string concatenation into markup anywhere in `buildWaitlistCtaLink`, `sortFilterValues`, or the ABV chip path, matching the existing `createFilterButton` idiom |
