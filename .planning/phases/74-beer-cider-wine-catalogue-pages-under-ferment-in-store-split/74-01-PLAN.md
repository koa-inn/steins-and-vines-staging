<objective>
Close the live information-disclosure defect on `GET /api/recipes` and `GET /api/recipes/:id` before Phase 74 publishes the first public recipe surface.

Today both routes are unauthenticated and ungated: `GET /api/recipes?status=all` returns all 10 recipes (9 of them `draft`) with `computed_price` to any anonymous caller, and `GET /api/recipes/:id` returns full ingredient-level detail for any recipe id regardless of status. This is verified live, not hypothetical.

Purpose: D-06 states the control must live at the endpoint, because a page-side filter is defeated by a query-string edit. D-07 states a public recipe may expose only name / style / price / blurb, so a status filter alone is insufficient — the response body itself must be projected through a field allowlist.
Output: a tier-aware read contract on both routes, plus a regression test file that proves it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous browser → `GET /api/recipes` | Untrusted, unauthenticated request. Exempt from the global `/api` guard (`server.js:288` lets every GET through), so the route must resolve its own credential. |
| anonymous browser → `GET /api/recipes/:id` | Same, plus an enumerable path parameter. |
| middleware → Apps Script `get_recipes` | Server-to-server, `server_token` authenticated. Untouched by this plan, but its `status` filtering is not trusted as the sole control. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-74-01 | Information Disclosure | `GET /api/recipes` | mitigate | Resolve tier via `authTiers.resolveTier`; non-staff callers get `status` forced to `'active'` before cache-key construction, AND the returned array is re-filtered on `status === 'active'` server-side so a stale/over-broad upstream or cached payload still cannot leak a draft |
| T-74-02 | Information Disclosure | `GET /api/recipes/:id` | mitigate | Non-staff request for a non-active recipe returns `404 {error:'Recipe not found'}`; active recipes return `{recipe}` with the `ingredients` key absent entirely |
| T-74-03 | Elevation of Privilege | `?status=` query parameter | mitigate | The client-supplied `status` is discarded for non-staff callers before it reaches the cache key or the Apps Script payload — a query-string edit has no effect |
| T-74-04 | Information Disclosure | cost/margin-derivable fields | mitigate | `toPublicRecipe` is an allowlist projection (build-new, never delete-from); price is collapsed to one fee-inclusive number so `locked_price` / `service_fee` / `materials_fee` cannot be recovered from the response |
| T-74-05 | Spoofing | staff tier resolution | transfer | Reuses `authTiers` unchanged (`apiKey.matches` is a length-checked `crypto.timingSafeEqual`; device token and session lookup unmodified). No new credential surface is introduced. |
| T-74-06 | Repudiation | tier-resolution failure | mitigate | `isRecipeStaff` catches a rejected `resolveTier` and resolves `false` — fails closed to the public projection rather than opening the staff path |
| T-74-07 | Denial of Service | Apps Script quota via the new public surface | accept | Existing 10-minute Redis cache is retained and anonymous traffic now collapses onto the single `sv:recipes:active:0:0` key, so public load reduces rather than increases upstream calls |
