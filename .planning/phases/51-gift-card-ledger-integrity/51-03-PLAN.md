<objective>
Get the ledger actually running in Google's environment, then prove behaviourally that it closes the
window — because nothing else can.

Purpose: 51-01 and 51-02 changed a file with no local execution environment. The Jest suite proves
the decision logic is right and the statements are in the right order; it proves nothing about
Sheets round-trips, because `SpreadsheetApp` does not exist outside Google, and the middleware suite
mocks `axios` before it ever reaches Apps Script (`pos-gift-card.test.js:18-21`).

The probes are deliberately asymmetric. A working redeem proves almost nothing — the old code did
that too. What must be proven is the DANGEROUS direction (D-11): that a second balance change is
REFUSED. Two separate refusals matter, and they are different mechanisms:
  - the same `transaction_ref` replayed (criterion 6), and
  - a crash-then-retry arriving with a DIFFERENT `transaction_ref` (criterion 7, D-12) — the case
    a ref-keyed guard misses entirely, and the whole reason this phase exists.
And a third thing must be proven that is not about refusal at all: that a stuck claim can be
CLEARED, because a certificate no customer can ever redeem again is a worse outcome than the bug.

Blast radius, stated honestly: one Apps Script deployment and one Google Sheet serve BOTH staging
and production (STATE.md:56). There is no staging gate for a `.gs` redeploy. The moment the owner
clicks Deploy this is live for kiosk, admin and BrewPad, on a path that debits real customers.

  <what-built>
    Gift-card redemptions and reloads now write a record BEFORE they touch the balance, and mark it
    settled afterwards. If the script is interrupted partway — a timeout, a quota, a transient
    Google error — the unfinished record stays behind, and the next redemption or reload on that
    certificate is REFUSED instead of moving the balance a second time.

    That refusal is the fix. Today, if the script dies after debiting a card but before writing its
    idempotency key, the next attempt sails straight through and debits the customer twice. Reload
    has the same shape and gives money away twice. This needs no concurrency at all — one
    interrupted run is enough.

    The refusal is deliberately not keyed on the transaction reference, because that reference is
    re-minted on every retry by design (the kiosk clears it on every error and the Retry button
    mints a fresh one). A reference-keyed guard would miss exactly the crash-then-retry case that
    matters. It is keyed on "does this certificate have an unfinished record" instead.

    There is also now a real audit trail — a `GiftCardTransactions` tab showing every redeem and
    reload with the balance before and after — which did not exist in any form before.

    **None of this is live yet.** `apps-script/adminApi.gs` lives in this repo but runs in Google's
    environment, and there is no CI deploy for it. Until you redeploy, production is running the old
    four-write code.

    **Blast radius:** one Apps Script deployment and one Google Sheet serve BOTH staging and
    production. There is no staging gate here — the moment you click Deploy this is live for kiosk,
    admin and BrewPad, on the path that moves real customers' gift-card money. That is why step 2
    records the previous version number first.

    **A deliberate trade you should know about:** the refusal fails CLOSED. If a record is left
    unfinished, that certificate cannot be redeemed until someone clears it. That is the right
    direction on a money path — refusing is recoverable, double-debiting a customer is not — but it
    does mean a stuck record temporarily blocks a real card. Clearing one is a single cell edit,
    documented in `docs/APPS_SCRIPT.md`, and Probe D makes you do it once so you have done it before
    you need it with a customer waiting.
  </what-built>
