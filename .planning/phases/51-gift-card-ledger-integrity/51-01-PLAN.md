Build the ledger substrate and — more importantly — the one piece of this phase that CAN be
genuinely tested locally: the idempotency decision, extracted as a pure function.

Purpose: `apps-script/adminApi.gs` has no local execution environment, and the middleware suite
mocks `axios` before it ever reaches Apps Script (`pos-gift-card.test.js:18-21`), so no test in this
repo can observe a Sheets write. STATE.md records a commit that passed its suite for four days
while dead in production for exactly that reason. The honest response is not to fake an end-to-end
test — it is to move as much of the decision as possible OUT of the Sheets-touching code and into a
pure function that a real Jest suite can hammer, then verify the rest by live probe (51-03).

`giftCardLedgerDecision` is that function. It receives ledger rows as a plain array and returns
`replay` / `blocked` / `proceed`. Every rule that matters for D-12 — replay detection, the
unsettled-claim fail-closed guard, and the staff escape hatch — lives inside it and is tested here.

Output: a new `tests/frontend/adminapi-giftcard-ledger.test.js` suite, plus the constant, four pure
helpers and the ledger IO helpers in `adminApi.gs`. Nothing in this plan changes `redeemGiftCard`
or `reloadGiftCard` — the money path is untouched until 51-02.

    `giftCardLedgerDecision(rows, certNumber, txRef)` — the core. Rules in priority order:
    - Empty rows array -> action 'proceed', row null, unsettled false.
    - Rows for a DIFFERENT cert only (including a claimed one) -> 'proceed'. Cert matching is via
      normalizeCertNumber on both sides, so ' gc-000001 ' matches 'GC-000001'.
    - A settled row with the same cert AND same tx_ref -> 'replay', row = that row. This is the
      criterion-6 case: an interleaved retry of the identical ref must not move money again.
    - **A row with the same cert AND same tx_ref whose status is anything OTHER than 'claimed'
      (e.g. 'resolved', 'cleared', '', a typo) -> 'replay', NOT 'proceed'.** A `tx_ref` that
      already appears anywhere in the ledger has been consumed, and the balance may already have
      moved under it. Without this rule the staff escape hatch below would silently un-protect the
      exact ref it just rescued: a 'resolved' row matches neither the settled-replay rule nor the
      claimed-blocked rule, so a resubmission of that same ref would fall through to 'proceed' and
      move money a second time — reopening this phase's own defect immediately after its sanctioned
      remedy is used. **The ONLY way to make a `tx_ref` usable again is to DELETE its row**, which
      is the documented full-reset remedy. Editing the status clears the block for NEW refs while
      preserving replay protection for the old one.
    - A claimed row for the cert with a DIFFERENT tx_ref, no settled match -> 'blocked',
      row = the claimed row, unsettled true. THIS IS THE D-12 CASE and the whole point of the
      phase: the ref was re-minted by the retry, so a ref-keyed guard would have said 'proceed'.
    - A claimed row for the cert with the SAME tx_ref -> 'blocked' (not 'replay'): the balance
      may or may not have moved, so fail closed rather than report a balance that may be wrong.
    - Both a settled same-ref row AND a separate claimed row -> 'replay' with unsettled true.
      Replay is a read-only no-op so it is safe to return, but the caller must be able to see the
      cert is dirty — hence the separate `unsettled` field rather than folding it into `action`.
    - The staff escape hatch: the same claimed row with status changed to 'resolved', 'RESOLVED',
      'cleared', '' or any other value -> no longer 'blocked' **for a NEW tx_ref**. Blocking
      requires `String(status).trim().toLowerCase() === 'claimed'` exactly. A deleted row likewise
      clears it. **Note the interaction with the same-ref rule above: after a status edit, a
      resubmission of the ORIGINAL ref still returns 'replay' (protected), while a genuinely new
      attempt with a fresh ref proceeds. Deleting the row is the only full reset.**
    - Status matching is case- and whitespace-insensitive: ' Claimed ' still blocks.
    - Rows missing a `status` key entirely -> treated as not-claimed, do not block.
