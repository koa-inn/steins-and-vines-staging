# Phase 78 — UI Design Contract

> Visual and interaction contract for the new BrewPad **Waitlist** tab (staff-facing queue view + status workflow for the beer waitlist). Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This is a static-HTML / vanilla-ES5 / hand-written-CSS project. No component library, no shadcn, no Tailwind.** BrewPad ships its own self-contained stylesheet (`css/brewpad.css`, "no dependency on admin.css or styles.css", line 2) with its own token set, distinct from the public-site tokens in `css/styles.css`. This contract's job is to EXTRACT and reuse BrewPad's existing patterns — the batch-status tap-to-cycle interaction, the tasks/batches toolbar, the readings-table inline-edit row, the confirm-sheet — not invent new ones. Every class/token below is cited to a `css/brewpad.css` or `js/brewpad.js` line read directly during this research session (2026-09-02). No new stylesheet is created; all new rules are additive, appended to `css/brewpad.css`.

**shadcn gate:** not applicable — this repo is static HTML/vanilla JS, not React/Next.js/Vite. No `components.json` exists and none should be added. `Tool: none`.

## Phase-Specific Decisions

### 1. Where the surface lives: 6th BrewPad tab, table layout (not a card/detail split)

**Decision:** Add "Waitlist" as a 6th entry in `.bp-tab-bar` (Dashboard, Batches, Tasks, Readings, Recipes, **Waitlist**), each still `flex:1` — six tabs at BrewPad's iPad-landscape usage width (~1024px+) gives ~170px per tab, which comfortably fits the existing icon+uppercase-label stack with no CSS changes to `.bp-tab-bar`/`.bp-tab` needed. The panel itself is a **single-pane table** (`#bp-panel-waitlist` → toolbar → table), not the Batches tab's list-pane/detail-pane split — D-08 explicitly scopes this phase to a standalone list with no linking, so there is no "detail" to drill into. A tap on a row's status badge acts in place (§2); there is no navigation to a second view. This keeps the surface proportionate to what D-08 asked for and avoids importing the two-pane layout machinery (`--bp-detail-width`, `bp-batch-detail-pane`) for a feature that doesn't need it.

**Rationale for table over cards:** the Batches tab uses cards because each batch carries a lot of heterogeneous state (vessel, schedule, tasks, Zoho link) best browsed as scannable chunks. A waitlist row is 5-6 flat fields (email, category, signed-up, status, synced, notes) — exactly the shape `.bp-readings-table`/`.bp-active-batches-table` already handle well, and a table's fixed columns make the "in order" queue position (§3) visually obvious as a leftmost column in a way a card grid would not.

### 2. Status transitions: tap-to-cycle badge (forward only) + separate danger Remove — NOT a dropdown, NOT free-standing buttons

CONTEXT.md left this to discretion. **Decision: reuse BrewPad's existing batch-status tap-to-cycle interaction exactly** (`js/brewpad.js:5690-5701`) rather than a dropdown or a row of buttons — this is the one interaction pattern already proven, tested, and muscle-memorized by staff on the exact same device (iPad, BrewPad) for the exact same shape of problem (advance a status, confirm, write, toast).

**One deliberate deviation from the batch pattern, and why:** the batch cycle is a true loop (`next = order[(idx + 1) % order.length]`) — `complete` cycles back to `primary`, because batch stages are cyclical in practice (a batch can be reopened). **The waitlist cycle is NOT a loop.** `waiting → contacted → booked` is a one-way progression; wrapping `booked` back to `waiting` would silently reopen a customer's spot, which is never correct. **Implementation:** `order = ['waiting', 'contacted', 'booked']`; when `cur === 'booked'`, the tap handler is a no-op (badge stays `bp-status-clickable` visually for consistency, but the click handler returns early with no confirm sheet, no write, no toast) — do **not** apply the `% order.length` wraparound. `removed` is never reached by tapping the badge at all; it is reached only through the separate Remove action below. This is a correctness-driven deviation, not a style choice — flag it in the plan so the executor doesn't "helpfully" copy the loop behavior verbatim.

**Remove is a separate, always-danger-styled affordance** (small `×` button per row, `.bp-reading-del`'s visual treatment), independent of the status badge, because D-05 treats `removed` as an exit from the queue, not a step in the progression — conflating it with the forward cycle (e.g. tapping `booked` to reach `removed`) would make the one truly destructive action reachable by the same low-friction tap used for routine progress, which is the wrong friction level for an irreversible action.

### 3. Queue position (#) — the literal "we work through the list in order" promise

**Decision:** leftmost table column, header `#`. Computed **client-side**, not server-stored: rank (1-based) among rows currently in `waiting` status only, sorted by signup timestamp ascending (oldest first). Rows in `contacted`/`booked`/`removed` show `—` in this column, not a number — once staff have acted on an entry it's no longer "next in line," so a stale number would be misleading. The table's **row order**, however, is always by signup timestamp ascending regardless of status (oldest first, for every row, including contacted/booked/removed) — so the visual order itself embodies the ordering promise even when the reader isn't looking at the `#` column, and staff scanning top-to-bottom always see the true signup sequence for audit purposes. Style: `#` uses `--stain` (the one place this phase uses the primary accent color on data, not on a control) at the same weight as `.bp-batch-id` (`font-weight:700`, `:648`), to make it scannable at a glance without a heavier treatment competing with the status badge.

### 4. Sync-state visibility (D-07 requirement made concrete)

**Decision:** a small pill per row, next to (not replacing) the email — `"✓ Synced"` (`--batch-info`/`--batch-info-bg`, same visual weight as `.bp-kiosk-badge`) or `"⚠ Not synced"` (`--batch-warning`/`--batch-warning-bg`). This is deliberately a **persistent, always-visible per-row indicator**, not a detail hidden behind a tap — D-07's whole point (per CONTEXT.md, citing Phase 51's criterion-2 lesson) is that a durable, *visible* cell beats a log line; hiding it behind an interaction would reproduce the same "invisible to staff" failure mode D-07 exists to fix, just one layer less invisible than a log line. The **"Not Synced" filter chip** (§Copywriting) is the second half of "filterable" — staff investigating drift can isolate every row needing manual MailerLite attention in one tap, without scrolling the full queue.

### 5. Category column — present in the schema, auto-suppressed in the UI for now

D-02 requires the schema to carry `category` from day one; the *UI* may filter to beer initially. **Decision:** render a `Category` column **only if the fetched data contains more than one distinct `category` value.** At launch (beer-only), this column and its header are omitted entirely — mirrors the existing self-suppression precedent already proven in this codebase for `buildFilterRow()` (a filter row hides itself, including its label, when it has nothing to filter on; cited in `74-UI-SPEC.md` and confirmed live). This means the moment cider/wine signups start landing in the same tab (a future phase, per D-02's design), the column reappears automatically with zero code change to this phase's rendering logic — the suppression is a data-driven `if (distinctCategories.length > 1)`, not a hardcoded "beer only" assumption baked into the table shape.

### 6. Empty description / notes handling

The `notes` column (D-08 free-text) shows the em-dash placeholder when empty (§Copywriting), truncated to one line with `text-overflow: ellipsis` when long (matches `.bp-batch-card-name`'s truncation treatment, `:642-651`), with a small pencil (`✎`) edit affordance reusing `.bp-reading-edit`'s exact visual/interaction shape — tap opens the row inline into an editable text input (`.bp-inline-input`) with Save/× actions, collapsing back to the (possibly truncated) rendered text on save or cancel. No modal, no separate view — this matches the low-ceremony level D-08 calls for ("standalone list with a free-text notes column," not a rich editor).

### 7. Loading / error states

- **Loading:** a single `<div class="bp-skeleton-block"></div>` in the panel body while the initial `get_waitlist` fetch is in flight — matches the Tasks and Recipes panels (flat-list panels use one block; only the Dashboard and Batch-detail panes, which render multiple visually distinct regions, use two stacked blocks with a taller second one).
- **Error (list fetch fails):** replace the panel body with the standard error copy (§Copywriting) — no retry button pattern currently exists elsewhere in BrewPad's panel-load error handling (`dp.innerHTML = '<div class="bp-detail-content"><p class="bp-empty">Failed: ' + escapeHTML(err.message) + '</p></div>'`, `js/brewpad.js:4305`) — mirror that exact shape: `<p class="bp-empty-state">Could not load the waitlist. Please try again.</p>`, no separate retry button; staff re-triggers by switching tabs away and back (existing sitewide BrewPad convention for panel-load failures — this phase does not introduce a new retry-button affordance where one doesn't already exist elsewhere).
- **Empty (zero real entries) vs. empty (filtered to zero):** two distinct copy strings, see §Copywriting — do not conflate "the waitlist has no one on it" with "your current filter matches nobody," which would misinform staff mid-shift into thinking the queue is empty when it's actually just filtered.

## Responsive / Accessibility Contract

- **Touch targets:** every new interactive element reuses an existing class that already satisfies BrewPad's 44px minimum: `.bp-filter-btn` (`min-height:44px`, `:552`), `.bp-search-input` (`min-height:44px`, `:588`), `.btn`/`.btn-secondary` (`min-height:44px`, `:98`/`:113`). The one net-new small control, the per-row Remove `×` button, follows `.bp-reading-del`'s existing precedent, which is **not** independently 44px (it's an icon-sized tap target inside a table cell, consistent with the readings table's existing edit/delete icons at the same scale) — this is an accepted, already-shipped exception class for dense-table icon actions, not a new deviation this phase introduces.
- **Status badge as the primary tap target:** `.bp-status-clickable` badges are small (padding `2px 8px`, `:405`) but this exactly matches the existing, already-shipped batch-status badge tap target on the same device — no new accessibility regression, since staff already successfully use this exact affordance for batch status today.
- **Focus states:** reuse BrewPad's sitewide `*:focus-visible { outline: 2px solid var(--stain); outline-offset: 2px; }` (`css/brewpad.css:87`) — applies automatically to every new interactive element with no extra CSS.
- **Semantic structure:** table uses `<table>`/`<thead>`/`<tbody>` with a real `aria-label` (mirrors `aria-label="Plato readings"`, `js/brewpad.js:6491`) — e.g. `aria-label="Beer waitlist"`. Status badges keep an `aria-label` describing the action (mirrors the existing batch pattern: `statusBadge.setAttribute('aria-label', 'Batch status: ' + label + '. Click to change.')`, adapted to `'Waitlist status: ' + label + '. Tap to advance.'`, and omitted/static for `booked` rows since they are no longer actionable per §2).
- **Contrast:** no new color pairing — every badge/pill color pairing reuses `--batch-*`/`--ink-*` custom properties already live on the Batches tab today at the same contrast ratios.
- **iPad Safari:** no new gesture, no new modal chrome — the confirm sheet (`showConfirmSheet`) and inline notes editor are both existing, already-verified-on-iPad-Safari BrewPad patterns (CLAUDE.md project context: "This is an iPad-Safari-used internal tool"). No pinch/swipe interactions introduced; `body { touch-action: pan-x pan-y }` (`:104`) is unaffected.
