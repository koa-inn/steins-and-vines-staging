<!-- THE PHASE 78 WAITLIST CONTRACT, as implemented by plans 78-01 / 78-02 / 78-03. -->

Waitlist tab header row, exact order:
  id | email | category | status | signed_up_at | mailerlite_synced | notes

  id                : uuid string, column A
  email             : lowercase-trimmed
  category          : 'beer'
  status            : 'waiting' | 'contacted' | 'booked' | 'removed'
  signed_up_at      : ISO-8601 UTC, e.g. 2026-08-14T17:05:00.000Z — THE queue-order key
  mailerlite_synced : TRUE / FALSE
  notes             : free text

Deployed actions:
  add_waitlist_entry      — POST doPost, server_token. NOT on the admin proxy.
  get_waitlist            — GET  doGet/handleReadAction, server_token. On the admin proxy (read).
  update_waitlist_status  — POST doPost, server_token. On the admin proxy (write).

DEPLOY TOPOLOGY (this is what makes the ordering below load-bearing):
  zoho-middleware/**  auto-deploys to the STAGING Railway middleware on `git push origin main`,
                      and to PRODUCTION on `git push production main --force`.
  apps-script/*.gs    has NO CI path. One Web App deployment serves BOTH staging and production.
                      A new middleware whitelist entry paired with an un-redeployed adminApi.gs
                      produces a clean `invalid_action` that looks like a bug but is not.
  Therefore: Apps Script redeploy FIRST, staging middleware SECOND, production LAST.
