1. `WAITLIST_STATUS_ORDER` — a top-level `var` array `['waiting', 'contacted', 'booked']`. Note it deliberately excludes `'removed'`: removed is an exit from the queue, not a step in the progression (D-05, UI-SPEC §2).

2. `WAITLIST_STATUS_LABELS` — `{ waiting: 'Waiting', contacted: 'Contacted', booked: 'Booked', removed: 'Removed' }`. Mirrors the existing `STATUS_LABELS` const convention.

3. `WAITLIST_STATUS_COLORS` — `{ waiting: 'neutral', contacted: 'warning', booked: 'success', removed: 'danger' }`, mapping to the already-shipped `.bp-status-badge--{neutral,warning,success,danger}` classes (UI-SPEC §Color).

4. `nextWaitlistStatus(current)` — returns the next status in `WAITLIST_STATUS_ORDER`, or `null` when there is none. Returns `null` for `'booked'`, `null` for `'removed'`, and `null` for any unknown value. THIS IS A ONE-WAY PROGRESSION: do NOT use `% WAITLIST_STATUS_ORDER.length`. The existing batch-status handler at `js/brewpad.js:5690-5714` does wrap around, and copying that here would silently reopen a booked customer's spot. This is a correctness-driven deviation from the analog, explicitly called out in UI-SPEC §Phase-Specific Decision 2.

5. `isWaitlistSynced(value)` — returns `true` for boolean `true` and for the trimmed case-insensitive strings `'true'`, `'yes'`, `'y'`, `'1'`, and for the number `1`; `false` otherwise. The Apps Script side already coerces this, but a hand-pasted D-04 backfill cell may reach the client as a string, so the client normalizes too.

6. `sortWaitlistRows(rows)` — returns a NEW array (do not mutate the input) sorted by `signed_up_at` ascending, oldest first, comparing the raw ISO strings. Rows with a missing or unparseable `signed_up_at` sort LAST, in their original relative order, so a backfilled undated row never displaces a dated one from the front of the queue. Sort order is by signup time regardless of status — UI-SPEC §3 requires the visual order to embody the ordering promise for every row, including contacted/booked/removed.

7. `computeWaitlistQueuePositions(sortedRows)` — returns an array of the same length whose element `i` is the 1-based rank of `sortedRows[i]` among rows whose `status === 'waiting'`, or `null` for any row not in `waiting`. So a list of `[waiting, booked, waiting, removed, waiting]` yields `[1, null, 2, null, 3]`. Per UI-SPEC §3 a number is shown only while the entry is still genuinely next in line; a stale number on an already-contacted entry would mislead staff.

8. `filterWaitlistRows(rows, statusFilter, searchText)` — returns the subset matching both criteria. `statusFilter` is one of `'all'`, `'waiting'`, `'contacted'`, `'booked'`, `'removed'`, `'notSynced'`; `'all'` matches everything, `'notSynced'` matches rows where `isWaitlistSynced(row.mailerlite_synced)` is false regardless of status, and the four status values match `row.status` exactly. `searchText` is matched case-insensitively as a substring against `row.email` after trimming; an empty or whitespace-only search matches everything. Preserves input order.

9. `shouldShowWaitlistCategoryColumn(rows)` — returns `true` only when the rows contain more than one distinct non-empty `category` value (compared trimmed and lowercased). At launch, beer-only data returns `false` and the column and its header are omitted entirely; the moment cider or wine rows land in the same tab the column reappears with no code change (D-02, UI-SPEC §5).
