<objective>
Get the batched `updateRecipe` actually running in Google's environment, then prove behaviourally
that it works — because nothing else can. This is the only plan in Phase 79 that produces evidence
about the real system.

Purpose: 79-02 and 79-03 changed a file that has no local execution environment. `npm test` proves
the pure helpers are right and the file parses; it proves nothing about Sheets round-trips,
because there is no `SpreadsheetApp` outside Google. The two probes that matter are asymmetric:
if the comparison is too STRICT the save stays slow and announces itself, but if it is too LOOSE
the save returns 200 while silently discarding the user's ingredient edits. This plan tests both
directions explicitly, and observes the runtime branch directly rather than inferring it from a
stopwatch.

staging and production** (STATE.md:56). There is no staging gate for a `.gs` redeploy. The moment
the owner clicks Deploy, this is live for every surface — kiosk, admin, BrewPad. The rollback path
is the same dialog, which is why the previous version number is recorded before deploying.

  <what-built>
    `updateRecipe` in `apps-script/adminApi.gs` was rewritten to do roughly 6 Google Sheets
    operations per save instead of ~54. Specifically: it now compares the incoming ingredient list
    against what is already stored and skips the rewrite entirely when nothing changed (so renaming
    a recipe no longer deletes and recreates all 13 ingredient rows); it computes the next
    ingredient id once instead of scanning an entire column 13 times; it inserts in one write and
    deletes in one ranged call; it writes the recipe row once instead of ~14 times; it keeps your
    existing ingredient ids instead of minting new ones on every save; and it waits at most 5
    seconds for the script lock instead of 15, so a busy-sheet failure comes back fast and
    readable instead of impersonating the timeout.

    **None of this is live yet.** `apps-script/adminApi.gs` lives in this repo but runs in Google's
    environment, and there is no CI deploy for it. Until you redeploy, production is running the
    old code and every save still 502s.
