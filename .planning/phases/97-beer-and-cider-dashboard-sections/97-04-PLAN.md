<objective>
Serve the beer/cider card facts the aggregate cannot carry: abv, ibu, batch_size_l, juice, yeast per active batch, plus
the shared canning constants, on a new staff-only route GET /api/admin/dashboard-cards.

Purpose: D-07 needs ABV/IBU, D-12 needs juice/yeast picked by cf_type/cf_subcategory, D-09/D-10 need can counts from one
source. Design choice (deviation from RESEARCH, recorded here): RESEARCH proposed adding these to batchMeta inside
get_dashboard_stats, but existing tests pin that payload exactly (__tests__/db/batch-pg-dashboard-stats-96.test.js META_KEYS
and the Object.keys(res.data) list; __tests__/batch-dash-stats-route.test.js pins STATS_ACTION_TO_OP). Editing those is not
owner-approved (CLAUDE.md rule 10), so the facts ride on a separate read-only route. OG/target FG stay in batchMeta (already
sent). One extra Postgres read per dashboard load; no Zoho call.
Output: pure parser, PG read, store function, route module mounted in server.js, tests.

Response contract (consumed by plan 97-09):
200 { ok: true, cards: [ { batch_id, abv: number|null, ibu: number|null, batch_size_l: number|null, juice: string, yeast: string } ],
      canning: { packaged_litres: 25, brew_litres: 28, nominal: { "473": 52, "355": 70 } } }
When BATCHES_STORE is not postgres: 200 { ok: true, cards: [], canning: {...} }. On a read failure: 500 { ok: false, error: 'cards_unavailable' }.
</objective>
