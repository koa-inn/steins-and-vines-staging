<objective>
Build the server half of the packaging calendar: a staff-only route that lists upcoming Cal.com packaging bookings,
matches each to a batch by customer email on the server, caches the result, and fails soft (D-02, D-03, D-04).

Purpose: customer emails live on batches.customer_email / bottling_invite_email and in Cal.com attendees; matching must run
server-side so no email reaches the browser. The browser (plan 97-08) merges these bookings with BrewPad packaging tasks.
Output: pure matcher module, candidates SQL, store function, route, webhook invalidation, tests.

Discretion choices (CONTEXT: cache TTL and match rule):
- Window is server-computed (today..today+13 in America/Vancouver); the route takes no query params (less input surface).
  Cal.com is queried with a padded UTC window ((start-1 day)T00:00Z .. (end+2 days)T00:00Z) and each booking is then kept only
  if its Vancouver day is inside the window. This is DST-proof without offset arithmetic.
- Cache: Redis via lib/cache, TTL 300 s, key = PACKAGING_BOOKINGS_PREFIX + generation + ':' + windowStart. The generation is an
  in-process value initialised to Date.now() at module load and bumped by invalidate() (single Railway instance). This avoids
  cache.del in the webhook, whose existing tests pin "no cache.del" for BOOKING_CREATED and for undated cancellations.
- Status filter: drop bookings whose status is 'cancelled' or 'rejected' (case-insensitive) even though status=upcoming is requested.

Response contract (consumed by plan 97-08):
200 { ok: true, window: { start: 'YYYY-MM-DD', end: 'YYYY-MM-DD' }, truncated: boolean,
      bookings: [ { uid, start (ISO), end (ISO), day: 'YYYY-MM-DD', event_type_id: number, kind: 'bottling'|'canning', batch_id: string|null, customer_name: string } ] }
200 { ok: false, reason: 'not_configured' | 'unavailable' }
</objective>
